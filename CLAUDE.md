## Skills are the core unit — and `skillify` is how they are built

Almost everything here is a skill: a folder with `SKILL.md` (YAML frontmatter + body) and optional `schemas/`, `references/`, `templates/`, `scripts/`. Skills are authored/maintained via the **external `skillify` meta-skill** at `~/.claude/skills/skillify/`, and every skill must pass its two deterministic gates before it is considered done:

```bash
python3 ~/.claude/skills/skillify/scripts/quick_validate.py <skill-dir>   # frontmatter + structure
python3 ~/.claude/skills/skillify/scripts/check_links.py   <skill-dir>   # local reference links
```

House-style frontmatter (banking-grade skills, e.g. under `workflows/skills/`): `name`, `version`, `description` (must contain literal *"Use when …"* trigger phrases **and** *"Do NOT use …"* negative triggers, **no `<`/`>` angle brackets**), `stage_type`, `input_schema`, `output_schema`, a `banking_grade {idempotent, reversible, audit_level, pii_handling, tier_default, tier_adaptable}` block, `expected_duration_p95_seconds`, `max_retries_recommended`, `fallback`, `compatibility`. Body shape: Purpose → When to use (with explicit "not this skill" scoping) → Input → Procedure → Output (carries an `audit_id`) → Failure modes → Constraints → References → human approval gate/verdict. Keep `SKILL.md` ≤500 lines; push depth into `references/`.

Cross-skill references use **bare skill names** (so they survive folder moves). Skill output schemas thread an `audit_id` for the banking-grade audit trail.

## agentic-delivery-pipeline: declarative pipeline + Rust engine

> **ARCHIVED — historical/design reference only.** This whole tree (engine, `core/` schemas, `integration/`) is now under the sibling `../archive/agentic-delivery-pipeline/` (off-limits). The live pipeline is `workflows/delivery-pipeline.yaml` (+ `workflows/squad-delivery.yaml`) with boundary schemas in `workflows/schemas/`; there is **no live `squad-engine`** to run `validate`/`run`, so validation is static. The rest of this section documents the archived design.

The pipeline is data, the engine is code. **Layout:** the live tree (`engine/`, `core/`, `integration/`, the `*-squad/` skill folders) now lives under `agentic-delivery-pipeline/reference/`; only `.claude/` sits at the subproject root. `reference/integration/delivery-pipeline.yaml` (`apiVersion: cognitive-os/v1`) declares stages → `skill_ref` → typed input/output (`from_workflow_input` / `from_stage` field mapping) → per-stage `failure_policy` (`retry` | `loop_back` with cycle caps | `human-queue` | `skip` | `abort`) + SAGA `compensating_action`. It validates against `reference/core/schemas/workflow-v1.schema.json`. Stage handoff contracts are tabulated in `reference/integration/README.md`; deferred/placeholder stages and known divergences are tracked in `reference/integration/OPEN_ISSUES.md` and `reference/integration/WORKFLOW_GAP_ANALYSIS.md`.

`reference/engine/` (`squad-engine`, Rust/Tokio) is the runtime: event-driven concurrent scheduler (backend ∥ frontend legs run in parallel), per-stage JSON-Schema contract validation, content-addressed cache keyed on `sha256(skill_ref, version, prompt_version, input_hash)` (idempotent re-run / crash recovery), resumable `state.json`, and a tamper-evident audit trail (`run-log.md` + `audit-trace.jsonl`). Terminal states: `Done · WaitingHuman · Failed · HardFail · ShipWithCaveats`. `src/` is split by concern (`scheduler.rs`, `contracts.rs`, `policy.rs`, `compensation.rs`, `cache.rs`, `audit.rs`, `state.rs`, `graph.rs`, `executor/`).

```bash
cd agentic-delivery-pipeline/reference/engine
cargo build --release                                    # -> target/release/squad-engine
cargo test                                               # 4 e2e tests, MockExecutor, no LLM / no cost

squad-engine validate ../integration/delivery-pipeline.yaml          # native validate (yaml + schemas + skill_refs + graph)
squad-engine run ../integration/delivery-pipeline.yaml --input input.json --executor mock     # deterministic, no LLM
squad-engine run ../integration/delivery-pipeline.yaml --input input.json --executor claude   # REAL, billed claude CLI calls
#   add --unblock for full autopilot (never blocks on a human; can only end Done/ShipWithCaveats)
squad-engine status --run-dir <run-root>
squad-engine human list|resolve --run-dir <run-root> ...             # service the human-queue, then: run --resume
```

`run` exit codes: `0` Done/ShipWithCaveats · `2` WaitingHuman · `1` Failed/HardFail. Runs materialize **visible** per-stage deliverables under `reference/integration/runs/<run-id>/` (mechanical state under `.squad-run/`).

> **Security:** `--executor claude` runs each stage subprocess with `--dangerously-skip-permissions` (file + Bash). Run only on trusted pipelines/skills. `mock`/`stub` and the test suite never use it. `--unblock` disables contract enforcement for failing stages (degraded data can propagate) — opt-in, off by default; banking-grade human gates are the default.

## Stage outputs: dual-output review-doc templates

Templates **reuse, never copy** the canonical sources (BA story template, the `reference/repo-generator/` skeleton, the external `drawio` skill's house style, TL-handoff sub-templates, squad-flow-v0.7 blueprints). The 3 autonomous stages (S3, S4a, S4b) are **JSON-only** — readable doc advisory (template kept); see `LEAN_DECISION.md`.

**Per-stage human-view format policy** (recorded in the overview + `templates/README.md`): the human-view is a self-contained **offline HTML viewer** where review benefits from visualization (findings · evidence · metrics · rosters · maturity) — **only S1 is built**; S1.5 · S2.5 · S4a-r · S4b-r · S4c · S5 · S7 are **planned** (still `.md` today). Outputs whose native form *is* the right human-view stay as-is: **OpenAPI/structured** contracts (API-Path · event · request/response), **code + manifest**, **draw.io** architecture, **markdown** checklists.
